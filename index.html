The schema behind the numbers

modeled

You have real Salesforce and Snowflake access to check this against; I don't. So instead of guessing at your actual data, here's the schema I'd propose to produce every number in the funnel and rep sections above, plus two queries that, run against it, generate those exact figures. This is a design proposal, not a live connection.

Salesforce object/field schema + the queries behind the charts above
Opportunity (standard object, extended) ├─ StageName picklist Prospecting · Qualified · Demo · Proposal · Negotiation · Closed Won · Closed Lost │ (the funnel above only tracks the won path; Closed Lost still lives in the picklist) ├─ Segment__c picklist SMB · Enterprise (formula field off Account employee count / deal size) ├─ OwnerId lookup User (GTM rep through Qualified, reassigned to an AE by Flow on entry to Demo) ├─ Demo_Scheduled_Date__c date required to enter Demo ├─ Proposal_Sent_Date__c date required to enter Proposal ├─ Decision_Maker_Contact__c lookup Contact (required to enter Negotiation) ├─ Amount currency required to enter Proposal └─ CloseDate date required to enter Closed Won / Closed Lost Account (standard object, extended) └─ Payroll_Processing_Volume__c currency, rollup (written nightly from Snowflake, not sales-entered) int_pipeline_stages (Snowflake, built from the synced Opportunity object) one row per opportunity per stage it has passed through, with segment and stage_order. This is what the funnel and rep-performance sections above are actually queried from.

SMB vs. Enterprise, Closed Won

select segment, count(*) as closed_won from int_pipeline_stages where stage = 'Closed Won' and close_date >= date_trunc('quarter', current_date) group by segment
→ SMB 23, Enterprise 18, the exact split in the funnel chart above.

Qualified → Demo conversion

select count(*) filter (where stage_order >= 3) * 1.0 / count(*) filter (where stage_order >= 2) as rate from int_pipeline_stages
→ 210 / 340 = 62%, the same rate chained into the hiring-plan calculator above.

The dbt marts layer, built on top of int_pipeline_stages

fct_pipeline_stage (grain: one row per opportunity per stage entered) ├─ opportunity_id, stage, stage_order, segment, entered_at, rep_id ├─ is_current_stage boolean true for each opp's latest stage row └─ days_in_prior_stage number entered_at minus the prior stage's entered_at dim_rep (grain: one row per rep, rebuilt nightly from Workday + Salesforce User) ├─ rep_id, name, track enum AE · GTM ├─ title, start_date from the same LinkedIn/HRIS roster the hiring curve above is built from └─ ote_annual from the comp band this rep's title maps to, per the cost section above fct_hiring_cost (grain: one row per rep per day, the source for the cost + ramp charts above) ├─ rep_id, date, cumulative_cost dim_rep.ote_annual ÷ 365, accrued from start_date └─ cumulative_revenue ramped linearly over 120 days from start_date, then flat at the mature rate

Rep attainment rollup

select r.name, r.track, sum(o.amount) filter (where o.stage='Closed Won') as closed, r.quota_quarterly as quota from fct_pipeline_stage p join dim_rep r using (rep_id) join opportunity o using (opportunity_id) group by r.name, r.track, r.quota_quarterly
→ the quota/closed/attainment numbers behind every card in "Search a rep" above.

Cost per unit of revenue growth

select date_trunc('quarter', date) as qtr, sum(cumulative_cost) / nullif(sum(cumulative_revenue),0) as ratio from fct_hiring_cost group by 1 order by 1
→ the efficiency-index line in the Cost section above, before normalizing to Q2 '25.
